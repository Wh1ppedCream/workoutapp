# Classic → Material 3 Expressive: Component and Interaction Plan

**Decision:** keep Tonos Classic visually recognizable and investigate Material 3 Expressive (M3E) through interaction quality, component behavior, menus, and selective transitions. The target is **Classic that feels more expressive when used, without looking like a different app when still**.

This plan supersedes the earlier assumption that Classic needs a broad static redesign. The earlier M3E and Classic-modernization proposal files remain available as visual research; they are not deleted or rewritten by this plan.

## Scope and current baseline

This is a source-based audit, not an implementation brief for new visuals. It does not select another theme family, alter Classic tokens, or approve a third-party package. Layout, screen composition, navigation, content density, workflows, and semantic/data-color ownership remain the baseline.

Audit snapshot: `feature/classic-m3e` at `13c5e9c140226c8785e8bd390346f115b656f256`; local Flutter `3.29.3` / Dart `3.7.2`; `pubspec.yaml` declares Dart `^3.7.2`. These tool versions are below the currently documented standalone `material_ui` and `material_3_expressive` requirements; migration is a separate next task, not part of this audit.

### Current architecture and source of truth

- `MyApp` builds `MaterialApp` from `AppThemeFactory`; Classic currently derives its `ColorScheme` from `Colors.deepPurple` and attaches Tonos-owned semantic, surface, shape, data-visualization, and motion extensions. `AppMaterialTheme` uses standard Material 3 defaults (`ThemeData.from(..., useMaterial3: true)`). See [`main.dart`](../lib/main.dart), [`app_theme_factory.dart`](../lib/theme/app_theme_factory.dart), [`classic_theme.dart`](../lib/theme/classic_theme.dart), and [`app_material_theme.dart`](../lib/theme/app_material_theme.dart).
- Shared boundaries already exist for actions, surfaces, fields, dialogs, sheets, and navigation: [`TonosAction`](../lib/theme/widgets/tonos_action.dart), [`TonosSurface`](../lib/theme/widgets/tonos_surface.dart), [`TonosSection`](../lib/theme/widgets/tonos_section.dart), [`TonosField` / `TonosFormField`](../lib/theme/widgets/tonos_field.dart), [`TonosDialogFrame` / `TonosChoiceDialog`](../lib/theme/widgets/tonos_dialog.dart), [`TonosSheet`](../lib/theme/widgets/tonos_sheet.dart), [`TonosBottomNavigationBar`](../lib/widgets/tonos_bottom_navigation_bar.dart), and [`TonosTrainTabs`](../lib/widgets/tonos_train_tabs.dart).
- The default first-install destinations are **Train, Catalog, Logbook, Progress, Profile**. The user can configure tab order and visibility, so modernizing the bar must preserve both the default and the existing configuration behavior. `MainScreen` uses an `IndexedStack`; selecting a destination changes its index, not its route. See [`nav_bar_config.dart`](../lib/providers/nav_bar_config.dart) and [`main.dart`](../lib/main.dart).
- Active Workout is `SessionScreen` → `ExerciseCard` → `WeightCard`. The set rows, checkbox, weight/reps fields, Add Set action, exercise collapse control, and contextual menu belong to `WeightCard`, not a generic demo card. See [`session_screen.dart`](../lib/screens/exercise/session_screen.dart), [`exercise_card.dart`](../lib/widgets/exercise_card.dart), and [`weight_card.dart`](../lib/widgets/weight_card.dart).
- The Progress destination is `MeasurementsTrendsPage`, composed from the workout report, exercise progress, and health trends sections. It is not the separate hidden/optional Dashboard route. See [`measurements_trends_page.dart`](../lib/screens/measurements_trends_page.dart), [`workout_metric_chart_card.dart`](../lib/widgets/workout_metric_chart_card.dart), [`exercise_progress_section.dart`](../lib/widgets/exercise_progress_section.dart), and [`health_trends_section.dart`](../lib/widgets/health_trends_section.dart).
- Classic motion already has `AppMotionTokens` and `appMotionDuration`, which resolves to the theme’s reduced duration when `MediaQuery.disableAnimationsOf(context)` is true. New animation work should use this boundary. See [`app_motion_tokens.dart`](../lib/theme/tokens/app_motion_tokens.dart) and [`theme_extensions.dart`](../lib/theme/theme_extensions.dart).

## Modernization principle

Keep Classic’s purple identity, existing surfaces, layouts, plan/profile identity colors, success semantics, chart series, heatmap ownership, and dense workout workflow. Use M3E only when a response, selection, transition, or action treatment makes a real task clearer or faster. Prefer shared Tonos boundaries over direct package widgets in route code.

Do not globally replace cards, typography, shapes, app bars, or navigation to make still screenshots look more expressive. Do not add floating toolbars where Tonos has no selection workflow. Do not introduce a new palette or recolor charts, plans, settings categories, or completion states.

## Active Workout interaction plan

The active logger is the principal test of whether M3E helps or gets in the way. No proposal below changes its static card/set structure.

| Trigger | Proposed response | Motion and accessibility guard |
|---|---|---|
| Expand/collapse an exercise; auto-collapse when the final set completes | Reveal or remove only the set area and keep the exercise header/card identity stable. | Start with a bounded size transition around **160–220 ms**, using a damped curve with no visible bounce. Collapse in one composed update with the final completion state. Keep the list anchored; do not steal focus from a surviving field. Reduced motion: immediate layout change. |
| Mark/unmark one set complete | Use a quick check/fill state response, retaining Tonos semantic green and existing checked state. | Aim for **100–160 ms** at most, with no celebratory bounce or default haptic. Expose checked/unchecked and set number. Reduced motion: immediate state. Rapid toggling must never queue stale animation. |
| Add a set | Insert one row with a small reveal if it remains perceptually quiet. | Approximately **100–160 ms**; do not animate all card contents. Keep scroll position and typing focus; do not autofocus the newly added row unless a prototype demonstrates it improves the user’s normal logging sequence. Reduced motion: insert immediately. |
| Add Exercise FAB | Give the existing FAB a responsive press state, then use the current Catalog route. | Keep the route and the current selected exercise behavior. Do not replace this one-action route with a FAB menu. Reduced motion: no extra scale/morph; standard route transition remains accessible. |
| Exercise overflow | Open an anchored menu; close it before performing the existing remove-confirm or swap workflow. | Preserve anchor placement, Back/Escape and outside dismissal, and focus restoration. Do not move menu actions into a new toolbar. |
| Finish Workout | Show the existing busy state immediately; when save completes, present the current completion sheet. | No animation during an unknown save duration. Keep errors and “complete a set first” feedback unchanged. Reduce only the sheet/button transition when system motion is disabled; never delay the action. |

For prototypes, compare current standard Material against one M3E treatment at a time. Record time-to-log, visible sets per viewport, focus continuity, state comprehension, and reduced-motion behavior. If the component’s state layer or target size makes repeated logging slower, keep the current Material implementation.

## Progress and chart interaction plan

- Preserve the report’s three metrics (Workouts, Time, Volume), six date ranges, chart structure, selected bucket, and all current data-series/heatmap colors. Theme color is not chart-series ownership.
- The metric cards and chart pages already coordinate selection, and metric paging already calls `appMotionDuration`. Keep the existing page motion short; a selected metric should not trigger ornamental chart redraws.
- The range control is the narrow, high-value refinement: its six options currently animate fill over a fixed 160 ms. Use the existing motion helper so system reduced motion applies. Keep its compact six-column and narrow/large-text three-column arrangements.
- The custom chart already highlights a tapped bucket. Prefer a brief tooltip/point emphasis over interpolating the whole series when the selected range changes. A range change changes the data question; an animated line between unlike ranges can imply continuity that is not there.
- Do not count metric values up/down when ranges change. Keep exact values immediately legible; the selected state and chart page already tell the user what changed.
- `Additional Details` already uses a short reduced-motion-aware cross-fade. Keep it as-is unless a usability review finds a specific problem.
- Review keyboard and screen-reader access to the custom-painted chart point selection. Retain the chart’s touch behavior; expose the same selected bucket and value through semantics/focus if that path is currently missing.

## Toolbars, menus, dialogs, and sheets

1. **Keep current app-bar and drawer jobs.** Train’s top selector/profile drawer and Session’s timer drawer have different jobs. Keep their locations, routes, and contents. A floating toolbar is not a substitute for five-destination navigation and has no current multi-select workflow to serve.
2. **Prototype real anchored menus.** Exercise menus and preset menus already have an anchor and compact action list. Compare `PopupMenuButton`, current-stack `MenuAnchor`, and—after migration—a single `M3EMenu`. Judge focus, keyboard traversal, Back/Escape, dismissal, and action density before shape or motion.
3. **Keep the actual filter flow.** Catalog search is a debounced field and filtering is a dialog with multiple dropdowns. A search-app-bar pattern would replace the current interaction and is out of scope; refine existing field/menu focus only.
4. **Keep dialogs and sheets familiar.** Weight Units already uses the shared selected-radio choice dialog. Preserve its values and one-tap selection/close behavior. Session completion is already a modal sheet. Use shared Tonos dialog/sheet boundaries if a repeated behavior is changed; do not restyle every AlertDialog.
5. **Do not force split buttons.** Train’s Start and Optimize choices begin different workout flows, and Optimize settings are currently directly available. A split button would hide a frequent control or change the action model. Reconsider only if real usage data or a revised flow establishes one primary action plus a closely related alternate.

## Tonos motion policy proposal

Use the existing `AppMotionTokens` / `appMotionDuration` boundary. These are target bands for prototypes, not new tokens approved by this document.

| Class | Character and target | Spring/curve guidance | Reduced-motion behavior |
|---|---|---|---|
| **Micro interaction** — press, selection, checkbox, icon state | **80–160 ms**; feel immediate. | Prefer a standard ease or a very damped spring. No visible overshoot; do not block a second tap. | Resolve immediately using the existing reduced duration. Preserve clear selected/checked/disabled/focused visuals without movement. |
| **Component transition** — exercise expand/collapse, menu, segmented selection, sheet content | **150–230 ms**; express state or spatial relation, then get out of the way. | A lightly physical/damped spring may be tested for one high-value component. Avoid multi-stage choreography and repeated-set bounce. | Snap to final geometry; keep state and focus identical. If an M3E component cannot honor this, it is not ready for Tonos use. |
| **Route transition** — drill-down, Train → Session, completion | **200–280 ms** as a ceiling for a selective transition; current platform Material behavior remains the baseline. | Use conventional platform Material motion first; custom movement should explain the task relationship and be limited to named routes. | Remove movement (or use a platform-safe minimal transition) while preserving the route/back result. Never delay logging or save completion. |

System reduced motion is already read through `MediaQuery.disableAnimationsOf`. New custom controllers, shape morphs, animated fills, and package widgets must honor it rather than bypassing the helper. Keyboard activation, focus visibility/restoration, semantics state/value, 48 px target review, text scaling, contrast, and rapid repeated interaction are part of every prototype—not later polish. No default haptics are proposed for high-frequency set logging.

## Prioritized modernization map

### Tier 1 — first wave after the migration spike

1. **Tonos primary-action interaction.** Compare current Material press/focus/disabled behavior with a restrained expressive button at the existing Start/Finish sizes. Keep Start, Optimize, Finish, and busy semantics unchanged.
2. **Train tabs.** Prototype the existing two-choice `TonosTrainTabs` selection in place, checking 44/48 px fit, text scaling, semantics, and keyboard focus.
3. **Exercise expand/collapse.** Test the same `WeightCard` and same set rows with one bounded transition, including auto-collapse after final completion.
4. **Set completion and Add Set.** Evaluate rapid checkbox feedback and one-row insertion in the real dense logger; preserve success color ownership and field focus.
5. **Exercise/plan anchored menus.** Compare current popup with a standard anchored menu and one M3E menu behind a shared boundary. Keep action order, confirm behavior, and anchor placement.
6. **Progress selection.** Route the six-range selector through reduced-motion-aware timing; examine selected point/tooltip access and feedback without changing series colors or animating data meaning.

These first-wave items are interaction work, not permission to restyle all Classic buttons/cards/screens. If any prototype harms density, input focus, accessibility, or task speed, retain the current component.

### Tier 2 — useful after first-wave evidence

- Compare the current default bottom bar with standard `NavigationBar`; preserve five first-install destinations and user-configured tabs exactly.
- Try a subtle, explicitly scoped Train → Session or settings drill-down route transition against current platform Material motion.
- Review Weight Units dialog and Session completion sheet using standard Material radio/dialog/sheet updates; do not adopt M3E wrappers if the current selection and accessibility already work.
- Refine Catalog filter dropdown focus/anchoring and profile settings control state only when a concrete issue is observed.
- Revisit busy/progress feedback for longer optimization/generation operations if current progress is unclear; do not add wavy indicators to routine loading.

### Tier 3 — experimental

- `M3EFabMenu` against the existing two-destination `SpeedDialFab`, if Nutrition/measurement interactions enter the active product scope.
- Package-specific spring and shape behavior for a single component after reduced-motion, keyboard, text scaling, and frame-density checks pass.
- A selective route transformation only if a route prototype improves task orientation over the platform transition.

### Avoid or defer

- Replacing Start/Optimize with a split button or hiding Optimize settings in an overflow menu.
- Turning the single Add Exercise FAB into a menu, or replacing Resume/Exit with a generic FAB speed dial.
- Floating toolbars, center FABs, navigation rearrangement, route changes for bottom-nav taps, or a new action row.
- Replacing all card/surface/field/dialog shapes, global typography, or the Classic purple palette.
- Animated chart interpolation across different date-range datasets, broad page-transition springs, or expressive motion during every set edit.
- M3E widgets in workout rows until their touch/visual targets prove that the current number of sets remains visible and the logger remains as fast.
